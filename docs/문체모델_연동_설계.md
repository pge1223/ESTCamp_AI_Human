# 문체 모델 연동 설계

> 작성: 2026-06-08 · 담당 모델: 문체 모델 담당(문체 다듬기 모델)
> 관련: [기능정의서](기능정의서.md) F-EV-04/F-EV-05, [PROJECT_STATUS](PROJECT_STATUS.md)

대화/초안 텍스트를 작가 페르소나의 **문체로 다듬는 후처리 모델**을 시스템 어디에, 어떻게 붙일지 정의한다.

---

## 1. 모델의 역할 (후처리)

```
입력:  초안 텍스트(내용·구성 확정) + 타겟 작가(persona_id)
출력:  내용은 그대로, 문체만 그 작가 스타일로 다듬은 텍스트
```

- **내용 생성("무엇을 쓸지")** 과 **문체("어떻게 쓸지")** 를 분리하는 2단 파이프라인.
- 강사님 6/2 스크럼의 *"전후처리 모델을 끼면 성능 입증 가능"* 중 **후처리**에 해당.
- 원칙: **사건·대사를 바꾸지 않는다. 스타일만 변환한다.**

---

## 2. 부착 지점 비교

시스템의 텍스트 생성 지점은 3곳:

| 지점 | 기능 | 스트리밍 | 문체 후처리 적합도 |
|------|------|----------|-------------------|
| 소설 변환 (3단계) | F-NV-02 | ❌ 배치 | ⭐⭐⭐ **1순위 부착점** |
| 채팅 응답 (2단계, 대사/나레이션) | F-CH-03 | ✅ SSE | ⭐⭐ 트레이드오프 |

> 참고: 2단계 채팅은 AI가 등장인물 대사/작가 나레이션을 자동 구분하는 단일 응답 (모드 토글 없음). [사용자_시나리오](사용자_시나리오.md) 참고.

### 핵심 트레이드오프 — 스트리밍 충돌
후처리 모델은 **전체 텍스트를 받아야** 다듬을 수 있다. 반면 2단계 채팅 응답은 토큰을 실시간 SSE로 흘린다.
→ 후처리를 끼우면 "다 생성될 때까지 기다렸다 한 번에" 나와서 실시간 UX가 깨진다.
→ 따라서 **배치 작업인 소설 변환(3단계)이 1순위**. 문체가 가장 중요하고 UX 저하도 없다.

---

## 3. 전체 흐름

### 현재 (문체 모델 없음)
```
[2단계 채팅]
사용자 입력 → build_prompt → Gemini 생성 → SSE 스트리밍 → 화면
                                         └→ DB(Dialogue) 저장

[3단계 변환]
대화 로그 → generate_novel(Gemini) → 소설 초안 → DB(Novel)
```

### 변경 후 (소설 변환에 후처리 단 추가) ★ 추천
```
[3단계 변환]
                                  ┌──────────────────────────────┐
대화 로그 ─→ 1차 생성 ──초안──→  │  문체 모델                    │ ─→ 최종 소설 ─→ DB(Novel)
            (Gemini/Qwen)        │  · persona_id별 작가 문체      │
            "내용·구성"          │  · 내용 보존, 스타일만 변환     │
                                  └──────────────────────────────┘
                                            ↑ GPU 서빙(별도 엔드포인트)
```

### (선택) 2단계 채팅 응답까지 확장
```
채팅 입력 → Gemini 스트리밍(빠른 미리보기) → 화면에 먼저 표시
                        │
                        └─ 생성 완료 후 → 문체 모델 → 다듬은 최종본으로 교체 + 저장
```
실시간성을 살리면서 문체도 챙기는 "선표시 후교체" 방식. 구현 복잡도는 ↑.

## 4. 서빙 구조

FastAPI 앱과 모델 서버를 분리한다(배포·확장 독립).

```
┌──────────────┐    HTTP POST /refine     ┌────────────────────────┐
│  FastAPI     │ ───────────────────────→ │  문체 모델 서버(GPU)    │
│  LLMRouter   │ ←─────────────────────── │  Qwen 기반              │
└──────────────┘    { styled_text }        └────────────────────────┘
```

---

## 5. 코드 연결 지점

이미 존재하는 `LLMRouter.generate_novel`([backend/app/services/llm_router.py](../backend/app/services/llm_router.py))에 후처리 단 1곳만 추가:

```python
async def generate_novel(self, dialogue_history, world_description="", persona_id=None):
    draft = await _generate(build_novel_system(world_description), contents)  # 1차: 내용 생성 (personas.py)
    if persona_id and STYLE_MODEL_ENABLED:
        draft = await style_model.refine(draft, persona_id) # 2차: 문체 (문체 모델) ← 추가
    return draft
```

- 환경변수 `STYLE_MODEL_ENABLED`로 On/Off → 모델 준비 전엔 Gemini 단독으로 동작(폴백).

## 6. 인터페이스 계약 (문체 모델 담당과 합의 — 최우선)

부착 위치보다 **입출력 스펙**을 먼저 못 박아야 통합 시 안 깨진다.

```jsonc
// 요청
POST /refine
{
  "text": "다듬을 초안 전체",
  "persona_id": "baekya",   // 작가 4명 코드값 (백엔드와 동일하게 통일)
  "mode": "novel"           // novel | paragraph
}
// 응답
{ "styled_text": "문체 적용된 결과" }
```

합의 포인트:
- **persona_id 표기 통일** — `baekya / charoun / hanyeoreum / kimdohyeon` (과거 철자 불일치 이슈 있었음)
- **내용 보존 보장** — 사건·대사 변경 금지, 스타일만
- **지연(latency)** — GPU 추론 시간. 소설 변환은 단발이라 여유, 채팅 응답 확장 시 P95 < 5초 지표 고려
- **실패 시 폴백** — 모델 서버 다운/타임아웃이면 1차 초안 그대로 반환

---

## 7. 성능 입증 (발표용)

후처리 적용 **before/after**를 LLM-as-Judge([model/evaluation/llm_judge.py](../model/evaluation/llm_judge.py))로 채점:

```
초안(Gemini만)        → 페르소나 일관성 점수 X
초안 + 문체 모델 적용  → 페르소나 일관성 점수 Y   (Y > X 입증)
```

→ "문체 모델 적용으로 일관성 X→Y 상승" 정량 근거 확보 = 강사님이 말한 "성능 입증".
