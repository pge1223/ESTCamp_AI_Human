# 자기 평가서 — 가연 (백엔드 · 풀스택)

## 담당 역할
백엔드 코어(DB·세션·프롬프트) · 작가 페르소나 출력 품질 · Voice Mirroring · 삽화 생성 · 프론트 수정(채팅/메인/소설 목록)

## 한 일 (핵심)

**DB 아키텍처 설계 및 전환**
- 초기 PostgreSQL+MongoDB+Redis 이중 구조 설계·구현(Dialogue+RAG 임베딩은 MongoDB) → 이후 팀 결정으로 **MongoDB 완전 제거, PostgreSQL 단일화**로 재전환. `motor`·`sentence-transformers` 제거, 전 엔드포인트 SQLAlchemy로 복원
- **Neon 클라우드 DB 연동**: asyncpg가 `sslmode` 쿼리 파라미터를 지원하지 않는 문제를 `_prepare_db_url()`로 자동 변환 처리, Alembic도 동일 적용
- Alembic migration 다수 작성(`context_summary`, `World.tags`, `voice_profile` 등) + 체인 충돌(`down_revision` 분기) 해결, Windows asyncpg IPv6 연결 문제는 Docker exec 직접 SQL + migration 수동 작성으로 우회

**핵심 버그 — 근본 원인까지 추적**
- **StreamingResponse 내부 DB 저장 누락**: 로그상 저장 성공인데 실제 DB엔 안 남는 버그 → FastAPI `Depends(get_db)` 세션이 라우트 `return` 시점에 정리되는데 `StreamingResponse.generate()`는 그 *이후* ASGI가 소비하는 구조라 commit이 보장되지 않음을 규명, 독립 세션(`AsyncSessionLocal()`)으로 직접 commit하도록 수정
- **채팅 미러링 버그**: Redis가 `lpush`로 최신순 저장(index 0=최근)인데 코드가 `history[-1]`(가장 오래된 메시지)을 현재 유저 메시지로 착각해 제거 시도 → 제거 실패로 유저 메시지가 프롬프트에 중복 주입되어 AI가 따라 말하는 현상 발생, 인덱스 기준 수정
- **이어쓰기 작가 테마 미반영**: 다른 작가와 작업하던 세션을 이어써도 항상 백야로 표시 → 우측 패널의 `currentAuthorIdx`가 마운트 시 1회만 초기화되고 세션 로드 후 갱신되지 않던 것이 원인, 세션 로드 시 재계산하도록 수정
- **메인-채팅 CSS 클래스 충돌**: 메인 페이지 토글 버튼 작업 후 채팅 페이지 피드백 패널이 안 열리는 회귀 발생 → CSS가 전역이라 `main.css`의 `.author-panel-slide`(항상 화면 밖으로 트랜스폼)가 채팅의 `AuthorPanel` 컴포넌트와 클래스명이 겹쳐 덮어쓰던 것이 원인, `main-` 접두사로 네임스페이스 분리

**작가 페르소나 출력 품질**
- 등록된 등장인물이 채팅에 안 나오는 문제: "새 인물 임의 추가 금지" 규칙이 등록 인물까지 회피시킨 것 → "세계관에 없는 새 인물"로 한정해 해결
- 주인공 내면·대사를 AI가 대신 써버리는 문제: world_context 안에 묻혀 있던 규칙을 프롬프트 **최상단**(`[최우선 규칙 — 역할 구분]`)에 동적 주입하는 구조로 변경해 LLM이 실제로 따르게 함
- 화자(speaker) 표시 오류: JSON 응답 스키마에 필드가 없어 프론트가 첫 비주인공 이름으로 고정 표시하던 것을 스키마·파싱·SSE·프론트 전 구간에 `speaker` 필드 추가로 해결
- `personas.py`에 페르소나별 출력 규칙(동완님 작성 `personas_applied.py` 원고)을 적용하는 `load_persona_rule()` 메커니즘 구현 — 외부 규칙 파일 우선·내장 규칙 폴백, `compact` 옵션으로 캐릭터 모드 토큰 절약, `get_author_prompt()`/`build_novel_system()`에 연결. 한여름 few-shot 한 줄(직접적 신체 반응 → 외부 관찰 묘사)은 직접 교체

**Voice Mirroring (F-VM) — 사용자 말투 기반 대사 추천 (백엔드+프론트 풀스택 구현)**
- 2단계 설계: ① 샘플 문장 → 말투 프로파일 JSON 추출(원문 비저장·비복사 원칙) ② 프로파일+장면 맥락(7:3 비율) → 대사 후보 5종 생성
- `User.voice_profile` 컬럼 추가(세션이 아닌 유저 단위 데이터로 설계) + 마이그레이션
- **온보딩 페이지(`/voice-profile`) 신규 구현**: 메인 페이지 첫 진입 시 안내 팝업 → 샘플 문장 입력 폼 → 분석 결과 확인까지 전체 사용자 플로우, 폼 상태 localStorage 자동저장·복원 + 수정 모드
- 채팅 화면에 voice-suggest 연동: 프로파일 있으면 맞춤 대사 추천, 실패·미보유 시 기존 추천으로 자동 폴백, 추천 칩에 라벨 표시
- 마이페이지에 말투 카드(분석 요약·태그) + 내비게이션 항목 추가, 소설 목록 헤더에 마이페이지 바로가기 버튼 추가
- 마이페이지 말투 카드, 말투 설정 폼 localStorage 자동저장·복원 및 수정 모드 구현

**삽화 생성 기능**
- 백엔드 신규 구현: 직접 입력/AI 추천 2모드, 선정성·동떨어짐 필터링, 스타일×분위기×비율 조합, 읽기 페이지에 단계별 모달 UI 연동
- fal.ai 최초 연동 직접 구현(엔드포인트·필터링·UI 모달 전체) — 이후 데이터센터 IP 차단 이슈로 Vertex Gemini 2.5 Flash Image 전환은 jyj님이 진행, 가연은 그 사이 발생한 git stash 충돌을 upstream(Vertex) 버전 채택으로 해결

**기타 엔드포인트/기능**
- 토큰 사용량·비용 추적(`ApiLog`, 모델별 단가 계산, 일별 집계 API), 전역 에러 핸들링 미들웨어(모든 예외를 구조화된 JSON으로 통일)
- `ContextManager`(10턴 초과 시 대화 요약 주입), `World.tags` 자동 분류, `/stuck`(막힘 힌트), `/npc-react`(조연 다중 반응) 엔드포인트
- 메인 페이지 사이드바 드래그→토글 버튼 UX 개편, 소설 완결 기능을 목록/채팅/에디터 3곳에 동일한 사용자 경험으로 구현
- `chats.py`·`session.py` 등 다수의 브랜치 머지 충돌을 양쪽 변경사항 모두 보존하는 방식으로 해결

## 잘한 점

- **증상이 아닌 구조까지 추적**: StreamingResponse 세션 생명주기, CSS 전역 스코프, Redis 인덱스 순서처럼 "왜 되는 것처럼 보이는데 안 되는지"를 프레임워크/렌더링 동작 원리 수준까지 파고들어 재발 가능성 자체를 없앰
- **인프라 제약을 설계로 우회**: Neon SSL 파라미터, Alembic Windows IPv6 연결 문제마다 임시방편이 아니라 구조적 우회(URL 자동 변환, 독립 세션)로 해결
- **LLM 출력 제어를 프롬프트 설계로 해결**: "하지 마라"식 규칙 추가보다 정보를 어디에 어떤 강도로 배치하는지(최우선 규칙 동적 주입, 등록/미등록 인물 구분)가 실제 효과를 가른다는 것을 실험적으로 확인하고 적용

## 아쉬운 점 (약점 → 근거 → 개선 계획)

- **DB 아키텍처가 한 번 뒤집힘** — 초기 MongoDB+RAG 설계를 PostgreSQL 단일화로 되돌리며 이미 작성한 코드(Dialogue 모델, RAG 서비스 등)를 상당 부분 폐기. → *개선:* 다음엔 팀 합의 전 구현보다 작은 스파이크/PoC로 먼저 검증.
- **CSS 전역 스코프 문제를 사전에 방지 못함** — `panel-toggle-btn` 등 흔한 이름을 페이지 간 중복 사용해 회귀 버그를 직접 만들고서야 발견. → *개선:* 페이지 전용 클래스는 처음부터 페이지명 접두사 컨벤션을 강제.
- **자동 테스트 부재** — 미러링·화자 표시 등 회귀성 버그를 매번 수동 채팅 테스트로 발견. → *개선:* 핵심 프롬프트 출력 형식(speaker·narration·dialogue 파싱)에 대한 단위 테스트만이라도 우선 추가.

## 배운 점

- **FastAPI `Depends` 세션과 `StreamingResponse`의 생명주기는 다르다** — 응답 객체가 반환된 시점과 실제로 소비되는 시점이 분리된 구조에서는 트랜잭션 경계를 명시적으로 다시 그어야 한다.
- **CSS는 기본적으로 전역이다** — 컴포넌트 단위로 안전하다고 가정하면 안 되고, 클래스명 네임스페이스는 처음부터 설계해야 할 항목이지 나중에 고칠 문제가 아니다.
- **LLM은 규칙의 내용보다 배치(위치·강도)에 더 민감하게 반응한다** — 같은 제약이라도 프롬프트 어디에, 얼마나 구체적으로 넣는지에 따라 실제로 지켜지는지가 달라진다.
- **클라우드 인프라의 제약은 코드보다 먼저 연결/인증 모델을 이해해야 풀린다** — Neon SSL 파라미터, Alembic의 OS별 네트워크 동작 차이처럼 애플리케이션 코드 밖의 제약이 실제 막힘의 원인인 경우가 많았다.
