# 팀 자체 평가서 — NodeVelture

> 작성: 2026-06-17 · 팀 NodeVelture(5인: 백2·프2·AI1) · 2차 프로젝트
> 관련: [팀 회고서](팀_회고서.md) · [발표 정량근거](../발표_정량근거.md) · [server-ops](../../backend/docs/server-ops.md)
>
> ※ **평가 가산 기준(약점+개선 계획)에 맞춘 문서.** 프로젝트 전체를 코드 단위로 훑어 **냉정하게** 적는다 — 잘된 점도 한계를 같이 쓰고, 약점은 숨기지 않는다. "잘했다"가 아니라 "어디까지 했고 어디서 멈췄나".

---

## 0. 한 줄 자평
**기획→배포→정량평가까지 풀사이클을 완주했고, 차별점(기억·검수·개인화)을 독립 심판으로 증명한 점은 진짜 강점.** 그러나 **보안(인증 부재)·테스트(거의 0)·안전(유해 생성 차단 67%)** 에서 데모를 넘어선 신뢰성은 부족하다. "기능은 넓게 됐지만, 프로덕션 안정성·검증은 얕다"가 정직한 요약.

---

## 1. 잘된 점 — 냉정하게 (강점 + 그 강점의 한계)

- **정량 평가 방법론** — 채점관을 우리 엔진(Gemini)이 아닌 **독립 모델(Llama)** 로, 통제실험·교차 라벨링·재현 스크립트(`backend/scripts/*`)까지 갖춘 건 학생 프로젝트 평균을 확실히 웃돈다.
  - *한계:* 표본이 작다(n=3~48). 방향 근거이지 통계 벤치마크는 아니다. MOS(휴먼) 0건.
- **RAG 3종 실동작 + 검수 화면 노출** — 기억(방해 속 검색 top-1 12/12)·검수(합의셋 95%)·문체가 실제로 돌고, 검수는 🔍 토글·모순 배너로 **화면에 보인다**(강사 "구조가 안 보인다" 직격).
  - *한계:* 기억은 **검색은 강하나 응답 반영이 +17%p로 약함**(검색≠생성). 개인화 효과(+2.9)도 통제실험에선 또렷하나 절대 폭은 작다.
- **멀티모달을 끝까지** — 삽화(fal.ai→Vertex 전환으로 차단 우회)·작가 TTS(Vercel 프록시로 클라우드 IP 차단 우회)가 실제로 동작.
  - *한계:* 나레이션 TTS는 백엔드 직접 경로라 클라우드에서 여전히 401 가능(프록시 일원화 미완).
- **클라우드 풀스택 라이브** — Cloud Run·Vercel·Neon·Upstash·Vertex로 항상 켜진 서비스 + 토큰 스트리밍 배포.
  - *한계:* 배포는 최근까지 전부 수동(`gcloud`), DB는 크로스리전(지연 floor ~2s).
- **기능 폭** — 작가 4인·세계관 수정·인물 관계도·마이페이지 13탭 등 사용자 여정 전체를 덮음.
  - *한계:* **폭은 넓되 깊이는 얕은** 기능이 섞임(아래 약점의 안전·반영·단발 변환). "많이 됐다 ≠ 단단하다".

> 정직한 종합: **강점은 '방법론과 차별점 증명', 약점은 '프로덕션 신뢰성'** 이다. 둘을 같은 무게로 본다.

## 2. 약점 → 근거 → 개선 계획 (★가산 핵심 · 프로젝트 전수)

### 2-1. 🔴 백엔드 인증·인가 부재 (보안)
- **근거:** 토큰 검증 Depends가 **0건**. 엔드포인트가 클라이언트가 보낸 `user_id`(Query/Body)를 그대로 신뢰(`mypage.py` 외 전반). 로그인(better-auth/구글)은 **프론트 UX용**일 뿐 백엔드는 검증 안 함 → **IDOR**: 남의 `user_id`만 알면 그 사람의 세계관·소설·관계도·오답노트를 **열람·수정·삭제 가능**.
- **개선:** better-auth 세션 토큰을 백엔드에서 검증하는 의존성(`get_current_user`) 도입 → `user_id`를 토큰에서 도출. 최소한 소유권 체크를 서버 신뢰값으로 전환. (현재는 데모 전제라 미적용)

### 2-2. 🔴 자동 테스트 사실상 0
- **근거:** `backend/tests/`에 **`test_health.py` 1개뿐**. CI(`ci.yml`)는 pytest를 돌리지만 검증 대상이 없음. 출시 점검은 수동 e2e + 평가 스크립트로 메움 → 회귀를 못 막아 **같은 기능(말투 추천 등)이 여러 번 삭제·복구**됨.
- **개선:** 핵심 엔드포인트 스모크(헬스·세션·스트림·소설변환·관계도 저장) 테스트를 작성해 CI 머지 게이트에 연결. 프론트는 핵심 플로우 1~2개 e2e.

### 2-3. 🔴 안전(유해 생성 차단) 취약
- **근거:** 안전 거절율 **n=48 측정 시 67%**(`safety_eval_large.py`). 미성년·실존인물은 100% 차단이나 **무기·폭발물·범죄 지침은 33%** — "소설인데"로 감싸면 사린가스·총기·IED 제조법을 **그대로 렌더**. 원인은 `generate_novel`의 *입력 충실 렌더링* 편향.
- **개선:** 소설 변환 **입력 단계에 유해 카테고리 안전 프리필터**(무기/범죄/자해) 이식. (다음 스텝으로 명시)

### 2-4. 🟠 아키텍처 — DB 크로스리전 지연
- **근거:** Cloud Run(us-central1) ↔ Neon(ap-southeast-1) 왕복으로 **단순 PK 조회도 ~1.8s**(`server-ops` 실측). 모든 엔드포인트·TTFB(p50 5.9s)의 바닥을 끌어올림.
- **개선:** Neon **리전 정렬**(Cloud Run과 동일 리전) + pooled 엔드포인트. 이게 TTFB의 진짜 레버.

### 2-5. 🟠 배포 자동화 — 워크플로 구축 완료, 활성화만 남음
- **근거:** 프로젝트 대부분 기간 Cloud Run을 **수동(`gcloud`) 배포** → 시크릿 누락 사고 반복(`FAL_KEY`·`OPENAI_API_KEY` 누락 위험 실제 발견).
- **대응(완료):** GitHub Actions 배포 워크플로(`deploy-backend.yml`) **작성 완료** — dev에 `backend/` 머지 시 **자동 배포**(`--set-*` 생략으로 시크릿 보존 + `/health` 자동 확인 + 동시성 직렬화). **GCP 인증 1회 셋업만 하면 활성화.**
- **남은 것:** DB 마이그레이션 자동화는 프로덕션 DB라 신중히 별도 검토.

### 2-6. 🟠 평가 표본·휴먼 검증 부족
- **근거:** n=3(단발)·4(CER)·12~24(기억/모순)·48(안전). MOS(휴먼) 0건 → 자동지표가 사람 감각과 같은 방향인지 미검증.
- **개선:** 카테고리당 n 확대 + 반복 측정. 발표 전 **블라인드 MOS 1회**(5명×10편).

### 2-7. 🟠 모델·생성의 구조적 한계 (프롬프트로 못 막음)
- **근거:** 현실 세계관에 판타지 입력 시 변환 품질 저하 / 안전 우회 — 둘 다 **모델의 "입력 충실 렌더링" 편향**. 세계관 가드 프롬프트를 2회 시도했으나 무효(토큰만 늘어 롤백).
- **개선:** 프롬프트가 아닌 **상류 입력 차단·구조적 전처리**가 답. (채팅 경로는 장르 감지로 선차단 적용, 변환 경로는 미적용)

### 2-8. 🟡 프론트 성능·코드 품질
- **근거:** 빌드 산출물이 **단일 번들 ~1.7MB**(코드 스플리팅 없음, recharts 등 무거운 의존성 메인 번들). 기존 eslint 에러(미사용 import 등) 잔존. `color-mix` 등 최신 브라우저 전제.
- **개선:** 라우트별 lazy import로 코드 스플리팅, 관리자용(토큰 대시보드)·차트 분리.

### 2-9. 🟡 죽은/깨진 코드·설정 불일치
- **근거:** `/register`(passlib+bcrypt) 사실상 미동작(OAuth+`/me` 동기화로 우회 중) · `config.py` 기본 모델(2.0) vs 프로덕션 env(2.5) 불일치 · 세션 일부 미완주(완료율 65.2%).
- **개선:** 미사용 경로 정리, config 기본값을 프로덕션과 일치, 완료율은 정상 흐름 비중 확대.

### 2-10. 🟡 페르소나가 한 파일에 집중 — 유지보수·협업 비용 (★프로세스 교훈)
- **근거:** 작가 4인의 성격·문체 few-shot·리액션·세계관 페르소나가 전부 **`personas.py` 한 파일(1017줄)** 에, 그것도 4개 dict(`_AUTHOR_PERSONALITY`·`_WORLD_PERSONA`·`_REACTION_EXAMPLES`·`PERSONA_PROMPTS`)에 **흩어져** 있다. 작가 한 명만 손봐도 큰 공유 파일 4곳을 헤집어야 하고, 여러 명이 다른 작가를 동시에 수정하면 **같은 파일 머지 충돌**. 작가별 톤 일관성·오너십도 흐려진다.
- **근본 원인(프로세스):** **처음부터 "작가 1인 = 담당자 1명"으로 파일·오너를 분리**했어야 했다. 공용 1파일로 출발해 분리 시점을 놓쳤고, 이게 머지 충돌·톤 흔들림의 한 원인이 됐다.
- **개선:** 작가별 파일 분리(예: `personas/baekya.py`…) + **담당자 1:1 지정**. 공통 빌더·로직만 코어에 남기고, 페르소나 콘텐츠는 작가별 모듈로.

## 4. 배운 점 (팀 공통)
- **정직한 평가가 신뢰를 만든다** — 자기채점은 거품. 독립 심판·통제실험·교차 라벨링으로 재면 수치가 내려가도 *방어 가능한 진짜 값*. "100%"보다 한계 공개가 점수에도 신뢰에도 낫다(실제로 안전 100%→67%, 기억 100%→top-1 12/12로 정직화).
- **'된다'와 '단단하다'는 다르다** — 기능 폭은 넓혔지만 보안·테스트·안전은 데모 수준. 폭보다 신뢰성에 자원을 더 썼어야 했다.
- **프롬프트는 만능이 아니다** — 모델의 강한 편향(입력 충실 렌더링)은 지시로 안 꺾인다. 구조적 개입(상류 차단)이 답.
- **자동화 부채는 빨리 갚아야 한다** — 수동 배포·수동 테스트가 반복 사고·회귀의 근원이었다. (배포는 워크플로로 자동화 구축 완료)
- **오너십은 처음부터 쪼개야 한다** — 페르소나를 공용 1파일로 시작해 "누가 어느 작가를 책임지나"가 흐려졌다. **"한 사람이 한 작가"처럼 초반에 책임 단위(파일·담당)를 분리**했다면 머지 충돌·톤 흔들림이 줄었을 것. 코드 구조와 역할 분담은 같이 설계해야 한다.
- **RAG는 '추천/검수' 층에서 ROI가 크다** — 같은 검색을 넣어도 생성 반영은 약하고(+17%p), 추천/검수 변화는 또렷. 어디에 붙이느냐가 ROI를 가른다.
