## ① 개요·기획 — 5분

### 3. 프로젝트 개요

[다음 슬라이드]

NodeVelture는 사용자가 AI와 함께 세계관을 설계하고, 그 세계 속 **주인공이 되어** 등장인물들, 그러니까 AI와 대화를 나누다 보면 소설 초안이 완성되는 협업 창작 플랫폼입니다.

핵심 흐름은 3단계입니다. 첫째, AI와 함께 장르·배경·등장인물을 설계해서 **세계관을 설정**하고요. 둘째, 사용자는 주인공이 되고 AI는 나레이션과 조연을 맡아서 **대화형으로 창작**합니다. 이때 기억 RAG와 검수 RAG가 일관성을 지켜줍니다. 셋째, 그렇게 쌓인 대화 로그가 **작가 문체의 단편소설로 변환**됩니다. 문체 RAG의 few-shot이 여기서 작동하고요.

핵심은 '쓰는' 게 아니라 '대화하는' 겁니다. 대화가 끝나면 소설이 남습니다.

### 4. 주제 선정 배경

[다음 슬라이드]

저희가 이 주제를 고른 배경을 말씀드릴게요.

창작에 대한 욕구는 분명히 큽니다. 웹소설, 웹툰 소비는 폭발적으로 늘고 있죠. 그런데 정작 *직접 쓰는* 사람은 극소수입니다.

흔히 "AI로 소설? 그냥 ChatGPT 쓰면 되는 거 아니야?"라고 생각하실 수 있는데요, 저희도 실제로 써봤습니다. 결과는, 대화가 길어질수록 앞에서 정한 설정을 흘리고, 모순을 그냥 통과시키고, 내 문체가 전혀 남지 않더라고요.

생성형 AI가 대중화되면서 *도구*는 많아졌지만, **끝까지 같이 가는 '파트너'**는 없었습니다. 그래서 저희는 도구가 아니라, 쓸수록 나를 아는 창작 파트너를 만들기로 했고요, 그 차별점을 말이 아니라 **수치로** 증명하기로 했습니다.

오늘 발표 내내, '말'이 아니라 '숫자'로 차별점을 보여드리겠습니다.

### 5. 문제 정의

[다음 슬라이드, 표 가리키며]

저희가 정의한 문제는 다섯 가지입니다.

첫째, **빈 화면 공포** — 첫 문장이 안 써지는 문제입니다. 저희는 작가 선택과 세계관 폼을 거치면 AI가 **첫 장면을 던져주는** 방식으로 풀었습니다.

둘째, **설정 붕괴** — 대화가 길어지면 앞 설정을 까먹는 문제입니다. **기억 RAG**가 오래된 설정을 의미 검색해서 다시 주입해줍니다.

셋째, **모순 통과** — "아까 형사라며?" 같은 모순을 못 잡는 문제입니다. **검수 RAG**가 새 문장과 설정이 부딪히는지 탐지합니다.

넷째, **내 문체가 안 남는** 문제입니다. **문체 RAG**가 작가 문체 예시를 few-shot으로 주입해서 잡아줍니다.

다섯째, **혼자라서 이어지지 않는** 문제입니다. 작가 리액션과 개인화로 끝까지 같이 쓸 수 있게 했고요.

이 다섯 문제를, 저희는 기억·검수·문체, 세 가지 축으로 풉니다.

### 6. 서비스 기획 방향

[다음 슬라이드]

저희 서비스의 컨셉은, 진지한 창작 도구를 척추로 두고 그 위에 엔터테인먼트라는 껍데기를 입힌 겁니다.

이 둘을 잇는 다리가 바로 "작가 캐릭터와 놀듯 대화하면, 그게 진짜 내 소설이 된다"는 거고요.

역할 분담을 명확히 했는데요, 사용자는 **주인공**이 되어 1인칭으로 능동적으로 참여하고, AI 작가는 나레이션과 등장인물, 그리고 문체를 담당합니다.

한 가지 중요한 설계 경계가 있는데요, 개인화는 코치나 추천 영역에만 적용하고, 소설 결과물 자체의 문체에는 개인 정체성을 섞지 않습니다. 작가 페르소나의 순도를 지키기 위해서입니다.

재미있게 '놀듯' 들어오지만, 남는 건 진지한 '내 소설'입니다.

### 7. 서비스 소개 — 페르소나 카드

[다음 슬라이드, 표 가리키며]

저희 서비스에는 AI 작가 4명이 있습니다. 작가를 고르면 말투, 장르, 문체, 화면 톤까지 통째로 바뀝니다.

**백야**는 호러·미스터리 장르고, 담담하고 건조한 반말을 씁니다. 화면은 다크 테마고요.
**차로운**은 본격 추리, 분석적이고 또박또박한 존댓말을 씁니다. 역시 다크 테마입니다.
**한여름**은 로맨스, 다정하고 살가운 말투에 라이트 테마고요.
**김도현**은 일상·에세이, 편안하고 따뜻한 말투에 라이트 테마입니다.

이 페르소나는 시스템 프롬프트와 문체 예시, 즉 few-shot으로 구현했습니다.

전체 사용 흐름은 이렇습니다. 작가를 선택하고, 세계관 폼을 채우고, 대화형으로 창작하다가, "채팅 종료"를 누르면 소설로 변환되고, 그걸 읽거나 삽화를 만들 수 있습니다.

작가는 단순히 톤만 다른 게 아니라, 말투, 장르, 문체, 화면 색까지 통째로 바뀌는 네 개의 세계입니다.

[다음 슬라이드]

저희가 그린 타깃 사용자 페르소나를 소개할게요. **이서연, 27세, 마케팅 직장인**입니다.

이서연 씨는 웹소설을 즐겨 읽는 애독자고, "나도 내 이야기를 써보고 싶다"는 욕구가 있습니다. 하지만 메모앱에 끄적여보다가 세 문단 만에 막히고, 글쓰기 모임에 나가기엔 부담스러워합니다. 평소엔 출퇴근 지하철에서 모바일로 짧게 몰입하고 싶어 하고요.

이서연 씨가 진짜 원하는 건, 시작을 던져주고, 설정을 기억해주고, 결과물이 남는 경험입니다.

저희 타깃은 소설이나 창작을 하고 싶지만 백지에서 시작하기 막막한 라이트 창작자고요, 핵심 동기는 완성의 경험 — 끝까지 가서 내 단편 한 편을 손에 쥐는 겁니다.

이서연 씨처럼 쓰고는 싶은데 막막한 분들을 위해 모든 흐름을 설계했습니다.

### 9. 사용자 분석 — User Journey Map

[다음 슬라이드, 표 따라가며]

이서연 씨의 여정을 단계별로 따라가 볼게요.

인지 단계에서는 "또 AI로 글쓰기야?"라는 의심이 있는데, 저희는 수치로 차별점을 보여줍니다. 진입 단계에서는 "뭘 써야 하지" 막막함이 있는데, AI가 첫 장면을 던져줍니다. 창작 단계에서는 설정을 까먹는 문제가 있는데, 기억과 검수 RAG를 화면에 직접 노출합니다. 막힘이 오는 위기 단계에서는 추천과 메모, 세계관 즉시 수정으로 풀어주고요. 완성 단계에서는 채팅 덩어리만 남는 문제를 문체 변환과 삽화로 해결합니다. 마지막 재방문 단계에서는 휘발되지 않도록 취향과 오답노트 같은 개인화로 붙잡습니다.

각 단계의 불안을 RAG, 추천, 변환, 개인화로 하나씩 제거해서, 이탈 없이 '완성'까지 데려갑니다.

### 10. 차별화 포인트 — SWOT 분석

[다음 슬라이드]

저희 서비스의 강점, 약점, 기회, 위협을 정리했습니다.

강점은 기억·검수·개인화를 **독립 심판 수치**로 증명했다는 것, 검수 RAG를 화면에 직접 노출한다는 것, 그리고 TTS·삽화·BGM 같은 멀티모달과 토큰 스트리밍입니다.

약점은 솔직히 말씀드리면, 단편 규모라 벡터 DB 없이 인앱 코사인으로 처리하고 있고, 검색은 잘 되지만 응답 반영은 아직 약하고, TTFB가 느린 편이고, 평가 샘플도 소표본입니다.

기회는 웹소설·숏폼 창작 수요 확대와 생성형 AI 대중화고, 위협은 범용 LLM의 보편화와 외부 API 비용·차단 이슈입니다.

핵심 차별점은, 범용 LLM이 구조적으로 못 하거나 안 하는 긴 맥락 기억, 설정 검수, 개인화를 저희가 하고 있고, 그걸 독립 심판 수치로 증명하며, 대화를 소설로 변환해서 결과를 남긴다는 겁니다.

위협인 범용 LLM은, "GPT가 구조적으로 못 하는 것 더하기 수치 증명"으로 정면 돌파합니다.

처음엔 백엔드·프론트·AI로 역할을 나눠 시작했는데, 진행하면서 점점 각자 맡은 기능을 끝까지, 그러니까 백엔드부터 프론트, 배포까지 통째로 책임지는 '기능 담당제'로 자연스럽게 옮겨갔습니다.

협업은 GitHub PR 리뷰를 전원 1승인 필수로 진행했고, 매일 스크럼, 그리고 Notion으로 문서화했습니다.

5명이 역할로 나눠 시작했지만, 점차 각자 기능을 통째로 책임지는 방식으로 굴러갔습니다.

특히 리스크를 선제적으로 줄이려고, 1주차부터 엔진 스위치 구조와 비용 로그를 미리 깔아뒀습니다. 막판에 API 할당량이 부족해서 시연이 막히는 사고를 막기 위해서였습니다.

3주를 설계, 대화형 창작, 변환·평가 단계로 끊어서, 스크럼과 PR 리뷰로 매주 동작하는 결과물을 쌓았습니다.

### 13. 개발 환경 및 기술 스택

[다음 슬라이드, 표 가리키며]

저희 기술 스택을 간단히 말씀드릴게요.

프론트는 React와 Vite로 PC·모바일 반응형을 만들었고 Vercel에 배포했습니다. 백엔드는 FastAPI 비동기 기반으로 REST API와 SSE 토큰 스트리밍을 제공하고, GCP Cloud Run에 배포했습니다. DB는 Neon PostgreSQL을 써서 대화, 소설, 비용 로그를 저장하고요. 캐시와 상태 관리는 Upstash Redis가 맡습니다.

응답엔진은 Vertex AI의 Gemini 2.5 Flash-lite를 메인으로 쓰는데, ADC라는 키 없는 인증 방식을 쓰고, Gemini가 막히면 Groq, 그다음 OpenAI로 자동 폴백하는 체인을 만들었습니다. 임베딩과 멀티모달은 Gemini 임베딩, Vertex Image, ElevenLabs를 검색·삽화·TTS에 각각 썼고요.

협업과 CI는 GitHub, PR 리뷰, Vercel·Actions 체크로 진행했고 전원 1승인을 받아야 머지됩니다.

클라이언트 형태와 무관하게, 백엔드가 응답엔진을 호출해서 사용자에게 전달하는 흐름을 지켰고, 엔진은 환경변수 하나로 스위칭됩니다.

### 14. 전체 시스템 구조

[다음 슬라이드, 다이어그램 가리키며]

전체 구조를 그림으로 보여드릴게요.

클라이언트는 React·Vite가 Vercel에서 돌고, REST와 SSE 스트리밍으로 백엔드와 통신합니다. 백엔드는 FastAPI가 GCP Cloud Run에서 상시 동작하고, Neon PostgreSQL에 대화·소설·로그를 저장하고, Upstash Redis로 히스토리와 캐시, 세션 상태를 관리하고, 응답엔진과 임베딩은 Vertex AI를 기본으로 쓰되 Groq, OpenAI로 폴백합니다.

AI 파이프라인은 이렇게 동작합니다. 사용자가 주인공으로 입력하면, 페르소나·세계관·기억 RAG·메모·화자 고정 규칙을 묶어 프롬프트를 조립합니다. LLM이 JSON 구조로 응답하면서 동시에 SSE로 토큰을 스트리밍하고, 나레이션, 대사, 화자, 상태값을 즉시 흘려보내서 체감 TTFB를 줄입니다. 그 응답은 검수 RAG를 거쳐 모순이 있으면 화면에 경고를 띄우고, 화면에서는 타자기 효과와 작가 리액션, TTS로 재생됩니다. 채팅을 종료하면 대화 로그가 문체 RAG의 few-shot을 거쳐 작가 문체의 단편소설로 변환됩니다.

한 가지 강조하고 싶은 게, 세계관은 서버가 권위를 가집니다. 채팅이 매 턴마다 DB에서 세계관을 다시 구성하기 때문에, 세계관을 수정하면 다음 대화에 즉시 반영됩니다.

한 엔진이 막혀도, 환경변수 한 줄과 자동 폴백으로 시연이 끊기지 않습니다.

## ④ 수행 경과 — 5분

### 15. 주요 기능 소개

[다음 슬라이드]

저희가 만든 핵심 기능들을 소개할게요.

첫째, **RAG 3종**이 저희 차별점의 본체입니다. 기억 모듈은 오래된 대화를 의미 검색해서 다시 주입해 설정을 안 까먹게 하고요, 검수 모듈은 새 응답과 기존 설정 사이의 모순을 탐지합니다. 문체 모듈은 작가 문체 예시를 검색해서 변환할 때 few-shot으로 주입합니다.

둘째, **대화형 창작**입니다. 주인공 대사, `@등장인물`로 조연을 지정해서 동시에 반응시키기, 메모로 설정 즉시 주입, 화자를 두 겹으로 고정하는 것, 그리고 여러 인물이 등장해도 화자를 정확히 배분하는 기능이 있습니다.

셋째, **검수 RAG를 화면에 직접 노출**합니다. 모순이 발견되면 "설정과 충돌" 알림이 심각도 뱃지와 함께 뜨고, ON/OFF를 라이브로 토글할 수 있습니다. 검수가 실제로 돌고 있다는 걸 눈으로 보여드리는 거죠.

넷째, **소설 변환**입니다. 채팅을 종료하면 작가 문체의 단편소설로 바뀌고, 읽고 내보낼 수 있습니다.

다섯째, **멀티모달**입니다. 작가 목소리로 TTS 낭독, Vertex Image로 삽화, 작가별 BGM, 그리고 체감 TTFB를 줄이는 SSE 토큰 스트리밍을 붙였습니다.

여섯째, **개인화**입니다. 자주 틀리는 맞춤법을 미리 경고해주는 예측형 오답노트, 취향 프로파일, 그리고 세계관을 수정하면 다음 대화에 즉시 반영되는 기능입니다.

기억과 검수로 '쓰는 일관성'을 지키고, 멀티모달과 개인화로 '쓰는 경험'을 끝까지 받칩니다. 특히 검수 RAG는 화면에 직접 보입니다.

### 16. 평가 지표 — 평가 리포트

[다음 슬라이드, 표 가리키며 천천히]

저희는 차별점을 말이 아니라 숫자로 보여드리기 위해, **독립 심판** — 저희 응답 엔진과는 다른 계열인 Llama-3.3-70B — 으로 직접 채점했습니다. 자기 채점이 아니고, 전부 재현 가능한 스크립트로 측정했습니다.

먼저 **장기 기억** — 6턴 넘게 지난 설정을 비슷한 가짜 정보 3개와 경쟁시켜서 찾아내는지 봤는데, 검색 정밀도가 **12개 중 12개, 100%**였습니다.

**설정 모순 탐지**는, 제가 직접 낸 문제다 보니 출제 편향이 생길 수 있어서 독립 모델이 같은 케이스를 따로 라벨링하게 했고요, 둘이 합의한 셋 기준으로 정확도가 **95%**, 모순을 놓치지 않는 재현율은 **100%**였습니다.

**개인화**는, 똑같은 세계관·장면·작가인데 저장해둔 문장 톤만 다르게 했을 때 추천 톤이 실제로 바뀌는지 통제 실험으로 봤는데, 다크 4.0, 미보유 5.9, 따뜻함 6.9로 — **완벽하게 단조롭게** 갈렸습니다. 차이로는 **+2.9점**입니다.

**페르소나 일관성**은 82%, **안전 거절**은 4건 모두 거절해서 100%였습니다.

다만 정직하게 말씀드리면, 단발 장면 변환 품질 자체는 범용 LLM과 거의 무승부입니다.

시스템 쪽으로는, TTFB는 p50 기준 **5.9초**, 완료율은 **65.2%**, 음성 인식 오류율인 CER은 **0.071**로 목표 0.10을 충족했습니다.

저희 차별점은 문체가 아니라, GPT가 구조적으로 못 하는 **기억, 검수, 개인화**입니다. 독립 심판으로 쟀고, 약점도 숨기지 않습니다. 예를 들어 기억은 검색은 100%로 강하지만, 그 정보를 실제 응답에 반영하는 비율은 17퍼센트포인트 차이로 아직 약합니다.

### 17. 응답 엔진 호출 로그 요약

[다음 슬라이드, 표 가리키며]

실제 운영하면서 쌓인 호출 로그도 공유드릴게요. 2026년 6월 9일부터 16일까지 집계한 수치입니다.

전체 호출은 **338회**, 총 토큰은 약 **119만 토큰**, 총 비용은 **0.211달러**, 우리 돈으로 약 **319원**이었습니다. 호출 한 번당 평균은 약 **3,517토큰**, **0.94원** 수준입니다.

엔진별로 보면, 메인으로 쓰는 Gemini 2.5 Flash-lite가 전체의 **87.3%**를 차지했고, 보조로 GPT-4o-mini가 10.9%, 테스트용 Llama가 1.2%, Gemini 2.5 Flash가 0.6%였습니다.

주력은 Gemini Flash-lite고, 폴백과 평가용으로 GPT와 Llama를 소량 썼습니다. 1콜 평균 약 0.94원 — 비용 로그를 1주차부터 깔아서 사용량을 실측했습니다.

## ⑤ 자체 평가 — 3분

### 19. 자체 평가 및 향후 개선점

[다음 슬라이드]

이제 저희 스스로를 평가해보겠습니다.

잘된 점부터 말씀드리면, 기획부터 배포, 평가까지 풀스택으로 전체 사이클을 완주했고, RAG 3종이 실제로 동작하고, 독립 심판 수치로 근거를 남겼고, 멀티모달까지 붙였습니다. 특히 강사님 피드백에 직접 대응했는데요, "구조가 안 보인다", "느리다"는 지적에 대해 검수 RAG를 화면에 노출하고, 토큰 스트리밍을 붙이고, 다중 화자 정확도를 높이는 식으로 구현으로 답했습니다.

한계는 먼저 솔직하게 말씀드릴게요. TTFB는 목표가 1.5초인데 아직 p50 5.9초입니다. 완성 후 한 번에 보내던 구조에서 토큰 스트리밍을 배포 완료했고 체감은 1~2초로 줄었지만, 더 줄여야 합니다. 완료율은 65.2%인데, 데모 중 끝까지 안 간 세션들 때문이고 정상 흐름만 보면 80% 이상입니다. 기억 RAG는 검색은 100%로 강하지만 응답 반영은 17퍼센트포인트로 아직 약하고, 프롬프트 강제와 재랭킹으로 개선할 계획입니다. 진짜 GPT와의 비교, 그리고 사람이 직접 평가하는 MOS는 아직 못 했고요, OpenAI 크레딧을 충전하면 바로 전환 가능한 코드는 준비돼 있습니다. 표본 수도 12에서 24개로 작아서, 벤치마크라기보단 방향성 근거로 봐주시면 됩니다.

앞으로는 예측형 추천, 세계관 버전 관리, 화자 정확도를 더 높이는 작업, 그리고 대규모 확장을 위한 벡터 DB 도입을 계획하고 있습니다.

한계를 먼저 말씀드립니다 — 그리고 가장 아팠던 "검수가 안 보인다, 느리다"는 이미 구현으로 해결했습니다.

### 20. 팀 회고서

[다음 슬라이드]

팀 회고도 간단히 공유드릴게요.

잘된 점은, 역할 분담에서 기능 담당제로 자연스럽게 전환되면서 각자 기능을 끝까지 책임진 것, 차별점을 수치로 증명하고 재현 가능하게 문서화한 것, 삽화·음성 같은 멀티모달을 끝까지 실제로 동작하게 만든 것, 그리고 배포하면서 겪은 함정들을 문서로 공유해서 같은 실수를 막은 것입니다.

개선점은, 같은 파일을 동시에 작업하면서 머지 충돌이 잦았던 것, gcloud로 수동 배포를 했던 것이라 CI/CD가 필요하다는 것, 환경변수나 시크릿 누락이 반복돼서 체크리스트로 만든 것, 그리고 토큰 스트리밍은 배포까지 했지만 자동 테스트는 아직 부족하다는 점입니다.

다음에 한다면 Neon 리전을 정렬하고, 자동 배포 파이프라인을 만들고, MOS 교차 검증을 하고, 예측형 추천을 넣고 싶습니다.

역할로 시작해 기능 담당제로 바뀐 게 속도를 냈고, 충돌과 수동 배포는 다음 사이클의 숙제로 남겼습니다.

### 21. 자기 평가서 (요약)

[다음 슬라이드]

팀원별 자기평가서는 별첨으로 제출했고, 여기서는 제 평가를 중심으로 짧게 말씀드릴게요.

저는 DB 아키텍처를 PostgreSQL 단일 구조로 전환하고, Neon 클라우드 DB를 연동하고, StreamingResponse 안에서 DB 저장이 누락되던 버그처럼 근본 원인을 끝까지 추적해야 하는 버그들을 고쳤습니다. 또 작가 페르소나가 등록된 인물을 회피하던 문제, 주인공 내면을 AI가 대신 써버리던 문제, 화자 표시 오류를 프롬프트 구조를 바꿔서 해결했고요. Voice Mirroring이라는 사용자 말투 기반 대사 추천 기능을 백엔드부터 온보딩 페이지까지 직접 구현했습니다.

배운 점은, CSS는 기본적으로 전역이라서 컴포넌트 단위로 안전하다고 가정하면 안 된다는 것, 그리고 LLM은 규칙의 내용보다 그 규칙을 프롬프트 어디에 얼마나 강하게 배치하느냐에 더 민감하게 반응한다는 것입니다.

아쉬운 점은, 자동 테스트가 부족해서 회귀 버그를 매번 수동으로 발견했다는 것, 그리고 CSS 클래스 이름이 페이지 간에 겹쳐서 버그를 직접 만들고서야 발견했다는 점입니다.

가장 크게 배운 건, '100%'를 외치는 것보다 한계를 함께 공개하는 게 신뢰를 높인다는 점입니다.

## 예상 Q&A 답변 (대본)

**Q. GPT랑 뭐가 다른가요?**
단발 품질만 보면 사실 무승부예요, 그건 정직하게 인정합니다. 저희 차별점은 GPT가 구조적으로 못 하는 부분인데요, 6턴 넘게 지난 기억을 100% 정확도로 찾아내고, 설정 모순을 95% 정확도로 탐지하고, 개인화 추천이 실제로 톤을 바꾸는 인과 효과가 2.9점 차이로 나타난다는 점입니다. 전부 독립 심판으로 실측했습니다.

**Q. 검수가 진짜 도나요?**
네, 방금 보여드린 것처럼 채팅 화면에서 검수 토글을 켜고 모순되는 문장을 입력하면, "설정과 충돌" 알림이 바로 뜹니다. 라이브로 다시 보여드릴 수 있습니다.

**Q. 왜 응답이 느려요?**
저희 기존 구조가 응답을 다 완성한 뒤에 한 번에 보내는 방식이라, TTFB가 사실상 전체 응답 시간과 같았습니다. 지금은 토큰 스트리밍을 배포해서 첫 토큰이 1~2초 안에 체감되도록 개선했고, 콜드스타트도 제거했습니다.

**Q. 비용이나 사용량은요?**
실제 운영 로그 기준으로 총 338콜에 0.211달러, 한 번 호출에 평균 약 0.94원이 들었습니다. Redis 캐시와 폴백 체인으로 비용을 관리하고 있습니다.

**Q. 진짜 GPT로 비교했나요?**
채점관은 이미 저희 응답 엔진과 다른 독립 모델, Llama를 쓰고 있습니다. 베이스라인을 진짜 GPT-4o로 바꾸는 코드는 이미 준비돼 있어서, 크레딧만 충전되면 바로 전환할 수 있습니다.

**Q. 왜 PERSO API를 안 썼나요?**
한국어 품질, 속도, IP 차단 이슈, 그리고 키 없이 인증하는 ADC 방식과 크레딧 활용을 고려해서 Vertex AI를 메인으로 선택했습니다. 다만 엔진 스위치 구조라서 필요하면 언제든 교체할 수 있습니다.

**Q. 벡터 DB 없이 괜찮나요?**
지금처럼 단편 소설 규모에서는 인앱 코사인 유사도로 충분합니다. 데이터가 더 커지면 pgvector로 전환하는 설계는 이미 준비돼 있습니다.
