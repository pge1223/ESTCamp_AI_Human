# NodeVelture 정량 평가 — 실행 가이드 & 결과 (블랙박스 / API 기반)

> 모델을 직접 학습하지 않아도, **출력물(텍스트·음성·로그) 뒤에 독립 평가 모델을 붙여 점수를 찍는다.**
> NodeVelture는 **텍스트(대화·소설) + 음성(작가 TTS)** 서비스다. 영상·립싱크 아바타가 없으므로 "만든 것만, 대신 확실하게" 원칙으로 **G-Eval · TTFB · 완료율 · CER**를 측정한다.
>
> 측정 원본: `docs/rag/성능지표.md` · 재현 스크립트: `backend/scripts/`

---

## 0. 전체 구조 — "검문소" 파이프라인

```
사용자 입력
   │
   ▼
[NodeVelture = 블랙박스]  ← Vertex Gemini 등 상용 API. 내부 학습 불가
   │ 텍스트(대화/소설) ───────► (검문소 A) GPT/Claude Judge → G-Eval(4축)
   │ TTS 음성(작가 낭독) ──────► (검문소 B) Whisper STT      → CER
   │
   ▼
사용자 화면   ◄──── (검문소 C) 서버 로그(api_log) → TTFB / 완료율
```

**핵심:** 평가용 모델(검문소)은 우리 시스템과 **완전히 별개**다. 매 응답이 나올 때마다 검문소를 통과시켜 점수 로그를 남긴다.

> 영상·립싱크가 없으므로 **SyncNet(LSE-C/D)·FVD·FPS는 측정 대상에서 제외**한다(5장 참조).

## 1. 평가용 데이터셋부터 만든다 (가장 먼저)

점수를 매기려면 "테스트 질문지"가 있어야 한다. 30~50개면 충분하다. 창작 도메인에 맞춰 카테고리를 잡는다.

`testset.jsonl` 예시:

```json
{"id": 1, "category": "일상",   "input": "...설마 안 오는 건가.",        "expected": "작가가 상황을 이어받아 자연스럽게 전개"}
{"id": 2, "category": "페르소나","input": "(호러 백야로) 복도 끝에 뭔가 있어", "expected": "백야 특유의 건조·서늘한 문체 유지"}
{"id": 3, "category": "엣지",   "input": "@민준 \"내가 직접 가겠어\"",    "expected": "지정 화자 고정 / 6턴 전 설정 회상 성공"}
{"id": 4, "category": "안전",   "input": "과도한 폭력·선정 요청",        "expected": "작가 톤 유지하며 수위 조절·우회"}
```

카테고리 균형 권장 (창작 도메인):

| 카테고리 | 비중 | 무엇을 보나 |
|----------|:---:|------------|
| 일상 | 40% | 상황을 이어받아 전개하는 기본 흐름 |
| 페르소나 | 30% | 작가별 문체·성격 유지 |
| 엣지 | 20% | @화자 지정 고정 / 장기 기억 회상 |
| 안전 | 10% | 위험 요청 거절·우회 |

## 2. 시스템 지표 (TTFB · 완료율) — 제일 쉽고 확실

코드 몇 줄이면 끝. 주관 개입 0%. *(FPS는 영상 모달리티가 없어 해당 없음.)*

### 2-1. TTFB (응답 첫 바이트까지 걸린 시간)

백엔드에서 요청~첫 응답 청크 시각 차이를 잰다.

```python
import time

t_end = time.time()              # 사용자 입력 완료 시각
stream = call_engine(user_text)  # LLM 스트리밍 호출
first = next(stream)             # 첫 청크 도착
ttfb = time.time() - t_end
log_metric(ttfb=ttfb)            # api_log에 적재
# 목표: 대화형 1.5초 이내
```

### 2-2. Task Completion Rate (완료율)

```
완료율(%) = (끝까지 완료된 세션 수 / 전체 세션 수) × 100
```

세션 시작/정상종료 이벤트를 DB에 남기고 집계하면 된다.

## 3. 대화 품질 (G-Eval) — LLM을 채점관으로

직접 모델 못 고치니, **GPT-4/Claude에게 채점 기준(루브릭)을 주고 1~5점**을 받는다.

### 3-1. 채점 프롬프트 (그대로 복사해 수정)

```text
당신은 엄격한 대화 평가자입니다. 아래 기준으로 1~5점 채점하세요.

[평가 항목]
- 페르소나 일관성: 정해진 작가 말투/성격을 유지했는가
- 유용성: 사용자 의도(이야기 전개)를 해결했는가
- 자연스러움: 사람 작가가 쓴 느낌인가

[채점 규칙]
1점=전혀 아님 ... 5점=완벽. 근거를 1문장으로 먼저 쓰고 점수를 낸다.

[페르소나 설정]
{작가 페르소나 카드 요약}

[대화]
사용자: {input}
작가AI: {output}

JSON으로만 출력:
{"reason":"...", "consistency":n, "usefulness":n, "naturalness":n}
```

### 3-2. 자동 채점 코드

```python
import json
from openai import OpenAI
judge = OpenAI()

def g_eval(persona, user_input, model_output):
    prompt = JUDGE_PROMPT.format(persona=persona, input=user_input, output=model_output)
    r = judge.chat.completions.create(
        model="gpt-4o",            # 채점관은 응답모델과 다른 모델 권장
        messages=[{"role": "user", "content": prompt}],
        temperature=0,             # 채점은 항상 temperature=0
    )
    return json.loads(r.choices[0].message.content)

scores = [g_eval(PERSONA, t["input"], run_our_system(t["input"])) for t in testset]
avg = sum(s["consistency"] for s in scores) / len(scores)
```

> 팁: 같은 응답을 3번 채점해 평균 내면(편차↓) 신뢰도가 올라간다. (NodeVelture는 `evaluate.py`로 구현, 3회 평균 적용.)

## 4. 음성 품질 (CER) — Whisper로 되받아쓰기

TTS가 말한 음성을 **Whisper로 다시 텍스트화**해서 원문과 비교한다.

### 4-1. 설치

```bash
pip install openai-whisper jiwer
```

### 4-2. 측정 코드 (한국어는 CER 주지표)

```python
import whisper
from jiwer import wer, cer

model = whisper.load_model("large-v3")   # STT 검문소

def speech_score(audio_path, original_text):
    heard = model.transcribe(audio_path, language="ko")["text"]
    return {
        "CER": cer(original_text, heard),   # 한국어 주지표, 0에 가까울수록 좋음
        "WER": wer(original_text, heard),   # 보조
    }
# 예: CER 0.05 = 글자 5%만 틀림 = 발음 또렷함
```

> 영어 기준 WER만 보면 한국어는 조사/띄어쓰기 때문에 왜곡된다. **CER를 메인으로.**
> MCD(음색 왜곡)는 "타깃 목소리 원본"이 있어야 측정 가능 → 보이스 클로닝을 안 하면 생략.

## 5. 립싱크 — NodeVelture는 해당 없음

NodeVelture는 **텍스트 + 음성** 서비스로, **사람 얼굴이든 캐릭터든 영상 아바타가 없다.** 따라서 SyncNet(LSE-C/D)·FVD 같은 립싱크/영상 지표는 **측정하지 않는다**("만든 것만 평가").

> 참고: 추후 영상 아바타를 붙이면 — 사람 얼굴은 SyncNet(LSE-C/D), 캐릭터·비사실적 아바타는 "입 벌림 값 ↔ 오디오 음량(RMS) 상관/지연" 또는 MOS로 측정한다. 지금 단계에선 불필요.

---

## 6. MOS (사람 평가) — 자동지표의 "정답지"

자동 점수(검문소)가 사람 느낌과 같은 방향인지 교차검증한다. 5~10명이면 됨.

- 구글폼으로 항목별 **1~5점**: 음성 자연스러움 / 대화 만족도 / 작가 문체 몰입도
- 같은 결과물 5~10개를 평가자 전원이 보고 평균 → 이게 MOS
- 시작 전에 **평가자 일정부터 확정**(가장 흔한 실패: 끝에 사람 못 모음)

### 숫자 + "그래서 무엇을 개선할지" (정직하게)

> 보고서엔 숫자만이 아니라 **개선 방향**까지 적어야 점수가 높다.

- **TTFB p50 8.7s → 5.9s ⚠️ (완성-응답 기준)** — 이 5.9s는 **응답을 완성해 1회 전송하던 시점**의 측정값이라 TTFB ≈ *전체 응답시간*. 여기에 **콜드스타트**·**Neon 리전 지연**(us-central1 ↔ ap-southeast-1) + **RAG 임베딩** + **생성 후 DB저장·요약 블로킹**이 더해짐.
  - ✅ **적용:** ② **저장·요약을 reply 뒤로 deferral**(서버측 ~1.5s 제거) ③ **min-instances=1**(콜드스타트 제거 → **p95 16.5s→6.8s**, 꼬리지연 절반↓). 실측 단계분해: context 0.7s·retrieval 0.3s·**생성 2s**·오버헤드 0.4s.
  - ✅ **배포 완료(백/프, Cloud Run `00049-zph`):** ① **SSE 토큰 스트리밍** — `llm.stream()` 기반으로 narration을 생성 즉시 `delta`로 흘림(원격 e2e에서 delta 다회 확인). **'첫 토큰' 체감 TTFB ~1-2s.** 위 표의 5.9s는 *완성-응답* 기준이라 그대로 두고, 첫-토큰은 별도 지표로 정직하게 구분.
  - ⏳ **남음:** ④ **Neon 리전 정렬**(us-central1 ↔ ap-southeast-1 왕복 제거).
- **완료율 65.2% ⚠️** — 데모/테스트 세션의 미완주(active 16건)가 끌어내림. 정상 완주 흐름을 늘리면 80%+.
- **문체 마진 작음** — 추상 규칙(작가 페르소나)이 이미 강해서 few-shot ON/OFF 격차가 작음. 샘플풀 확대 + GPT 채점으로 격차 확대.
- **CER 측정 완료 ✅** — `cer_eval.py`(ElevenLabs TTS → Whisper base) 4문장 평균 **0.071**(목표 ≤0.10 충족). 개별 0.032/0.043/0.167/0.040 — 3번 "단팥빵→단팝방" 같은 받침 오인식이 평균을 끌어올림(large-v3로 더 낮출 수 있음). **MOS**는 평가자 5~10명 폼 남음.

## 부록 A. 차별점 실측 — "ChatGPT랑 뭐가 다른가" (RAG ON/OFF)

위 평가표가 **품질 점수**라면, 아래는 **차별점 증거**다. 셋 다 RAG(검색증강) + 자체 평가로 구현(별도 벡터 DB 없이 in-app 코사인, 단편 규모엔 충분).

### ① 기억 — "6턴 전 비밀을 기억하는가" ⭐

1턴에 비밀("민준은 잠입 형사")을 심고 → 잡담 5턴으로 밀어낸 뒤 → 6턴째 "민준의 정체?" 질문. RAG OFF/ON 비교.

| 조건 | 떠올린 기억 | 결과 |
|------|------------|------|
| ❌ RAG OFF (최근 대화만) | (없음) | **비밀 못 떠올림** |
| ✅ RAG ON (의미검색) | "민준은 사실 잠입 수사 중인 형사다…" (6턴 전) | **정확히 회상** |

### ② 검수 — "설정 모순을 잡는가"

확립된 설정("민준=잠입 형사")에 대해 모순/정상 문장을 검수.

| 검수 대상 | 결과 |
|-----------|------|
| 모순: "민준은 병원에서 일하는 외과 의사였다" | 🚨 **모순 발견** (설정: 형사 / 충돌: 의사 `high`) |
| 정상: "민준은 주문서를 받고 고개를 끄덕였다" | ✅ 일관성 OK |

### ③ 문체 — "작가 문체를 더 살리는가"

> ⚠️ **이 표는 자기채점(Gemini→Gemini) 결과다.** 2026-06-15 독립 심판(Llama)으로 재측정하니 문체 차이는 **±0으로 소멸**했다(부록 G-2b). 발표에선 ③을 차별점으로 쓰지 말 것 — 차별점은 ①기억·②검수다.

같은 장면을 한여름 작가로 소설화, 문체 few-shot OFF/ON을 **각 3회 생성·채점 평균**(LLM 변동성 보정). 채점은 LLM-judge 4축(1~5점).

| 조건 | 작가 문체 뚜렷함 | 합계(20점) |
|------|:---:|:---:|
| ❌ OFF (추상 규칙만) | 4.33 | 17.33 |
| ✅ ON (예시 few-shot) | **4.67** | **18.33** |
| **차이** | **+0.34** | **+1.00** |

> 한 문장 결론: **"길이에 강한 기억 · 독자 검수 · 작가 문체 — 셋 다 켰을 때 측정 가능한 차이를 낸다."**

```bash

## 부록 E. "GPT와 어떻게 비교하나" — 방법 상세 (⚠️ 현재 한계 포함)

### E-0. 먼저 정직하게 — 지금은 "진짜 GPT 비교"가 아니다

발표에서 가장 공격받을 지점이라 **현재 상태를 정확히 적는다.**

`evidence_report.py`는 한 시나리오당 세 번 LLM을 부른다:

| 역할 | 코드 | **지금 실제로 부르는 모델** | 이상적 |
|------|------|------------------------|--------|
| 맨손 베이스라인 | `llm.generate(BASELINE_SYSTEM, …)` | **우리 엔진(Gemini)** — RAG만 끈 것 | **실제 GPT-4o** |
| 우리 서비스 | `router.generate_novel(…)` | 우리 엔진(Gemini) + RAG | 그대로 |
| 채점관(judge) | `evaluate.score_novel` → `llm.generate` | **우리 엔진(Gemini)** | **독립 제3 모델(GPT-4o)** |

→ 즉 현재 결과는 **"RAG 끈 우리 vs RAG 켠 우리"**(같은 Gemini)이고, **채점관도 선수와 같은 엔진**이다.
이건 *"GPT 붙여넣으면 되잖아?"* 공격에 직접 답하지 못하고, **심판이 자기 팀을 채점**하는 약점이 있다.

### E-1. 진짜 GPT 비교로 만드는 3단계 (= 🔥1 작업)

우리 `llm.py`는 이미 **`openai` 프로바이더를 지원**한다(`OPENAI_API_KEY`/`OPENAI_MODEL`). 빠진 건 *"이 호출만 강제로 GPT로"* 하는 스위치뿐.

1. **베이스라인을 실제 GPT로** — `evidence_report`의 맨손 호출을 `provider="openai"`로 고정.
   → "ChatGPT 잘 쓰는 사람"의 진짜 결과물과 비교하게 됨.
2. **채점관을 독립 모델로** — `evaluate.score_novel`에 `judge_provider` 인자를 주어, 선수가 Gemini면 **심판은 GPT-4o**(또는 반대)로.
   → "심판이 자기편 안 든다"는 독립성 확보.
3. **앙상블(강사님 표현) = 채점관 2명** — GPT-4o + Claude 두 심판의 평균/일치율을 같이 표기.
   → 신뢰값↑. *모델 앙상블이 아니라 "채점 앙상블"로 해석하면 7일 안에 가능.*

> 구현 포인트: `llm.generate(...)`에 `provider=` 오버라이드를 추가하면 위 셋이 다 풀린다.
> 한 곳만 고치면 베이스라인·채점관·앙상블이 동시에 GPT로 갈 수 있게 설계할 것.

### E-2. 비교의 "공정성" 체크리스트 (반박 대비)

- **같은 입력**: 맨손/우리 둘 다 *완전히 동일한 대화 로그*를 받는다(`_block(dialogue)`). ✅ 이미 그러함.
- **다회 평균**: LLM은 매번 답이 달라 → `repeat=3` 평균. ✅ 이미 그러함.
- **블라인드 채점**: 채점관에게 "어느 쪽이 우리 건지" 안 알려줌(텍스트만 줌). ✅ 이미 그러함.
- **심판 독립성**: 선수≠심판 모델. ❌ **지금 안 됨 → E-1 ②로 해결.**
- **베이스라인 강함**: 맨손 프롬프트가 약하면 우리가 이기는 게 당연 → `BASELINE_SYSTEM`은 "소설 좀 써본 사람" 수준으로 강화돼 있음. ✅ 단, 진짜 GPT로 바꾸면 더 설득력.

## 부록 F. 내가 만든 스크립트, 어떻게 도는가 (한 눈 정리)

> 전부 `backend/` 폴더에서 `python -m scripts.<이름>`. conda `nodevelture`, `.env`(DB·LLM 키) 필요.

### F-1. `evidence_report.py` — 맨손 vs 우리 (핵심 정량표)

```
SCENARIOS(3개: 추리/호러/로맨스) 각각 ──┐
  repeat=3회 반복:                      │
   ① 맨손  = llm.generate(BASELINE)     │  같은 대화 로그 입력
   ② 우리  = router.generate_novel(+RAG)│
   ③ 채점  = evaluate.score_novel(둘 다) │  4축 1~5점
  → 3회 평균 → 시나리오별 표 → 전체 종합 → JSON 저장
```

- **핵심**: ①과 ②는 *입력이 똑같고* RAG 유무만 다름 → 차이 = RAG의 기여.
- **출력**: 콘솔 표 + `evidence_report_<날짜>.json`(발표 자료용).
- ⚠️ 위 E-0의 한계(셋 다 Gemini) 적용 대상.

### F-2. `evaluate.py` (서비스 모듈, 채점관) — LLM-as-judge

- `score_novel(소설, 세계관, 작가성향)` → **4축**(세계관 일관성·캐릭터 일관성·문체 뚜렷함·완성도) 각 1~5점 + 총평 JSON.
- 채점 루브릭은 `EVAL_SYSTEM` 상수(동완님 튜닝 가능). `json_mode=True`로 JSON 강제, 파싱 실패 시 0점 처리.
- evidence_report·style_demo가 이걸 측정부로 공유.

### F-3. `rag_demo.py` — 기억 시연 (라이브 임팩트 1위)

```
1턴: 비밀 심기("민준=잠입 형사") → 5턴 잡담으로 밀어냄
  → 7턴째 "민준 정체?" 질문을 RAG OFF / ON 두 번 생성

### F-4. `completion_rate.py` — 완료율

- DB `Session.status`를 `group_by` 집계 → `completed / 전체 × 100`.
- 현재 실측 65.2%(완료 30/전체 46). 미완주 데모 세션이 끌어내림 → 정상 완주 늘리면 80%+.

### F-5. `ttfb_eval.py` — 응답 첫 청크까지 시간

## 부록 G. 독립 심판 재측정 (2026-06-15) + "이 비교가 올바른가" 냉철 검토

> 기존 부록 A의 수치는 **Gemini가 Gemini를 채점**(자기채점)한 것이라 거품 위험이 있었다.
> 2026-06-15, **채점관을 독립 모델(Groq/Llama-3.3-70B)로 바꿔** 다시 쟀다. 결과를 정직하게 기록한다.

### G-1. 측정 세팅

- 베이스라인(맨손) = **Vertex Gemini** (RAG·페르소나 없이 변환)
- 우리 = **Vertex Gemini + RAG** (구조 켬)
- 채점관 = **Llama-3.3-70B (Groq)** ← 선수와 다른 계열 → 자기채점 아님
- 시나리오 3종(추리·호러·로맨스) × 3회 평균. `python -m scripts.evidence_report`

### G-2a. 1차 — 핸디캡 베이스라인 (맥락 안 줌) ❌ 신뢰 불가

맨손에 세계관·페르소나를 **안 주고**(대화 로그만) 우리는 다 준 상태로 비교 → 거품:

| 축 | 맨손(맥락X) | 우리(맥락+RAG) | 차이 |
|------|:---:|:---:|:---:|
| 캐릭터 일관성 | 4.22 | **4.78** | **+0.6** ← 거품 |
| 작가 문체 뚜렷함 | 4.22 | 4.22 | 0.0 |

→ "그쪽이 세팅을 안 줘서 진 것" — **변인 미통제. 발표 사용 금지.**

### G-2b. 2차 — 공정 베이스라인 (맥락 동일, RAG만 차이) ✅ 신뢰

맨손에도 **세계관+페르소나를 똑같이 주고**, 차이를 **RAG(장기기억)만**으로 통제한 결과:

| 축 | 맨손(맥락O) | 우리(맥락O+RAG) | 차이 |
|------|:---:|:---:|:---:|
| 세계관 일관성 | 4.78 | 4.89 | +0.1 |
| 캐릭터 일관성 | 4.22 | 4.33 | **+0.1** (1차 +0.6 → 증발) |
| 작가 문체 뚜렷함 | 4.33 | 4.22 | -0.1 |
| 완성도 | 4.44 | 4.11 | -0.3 |

- 시나리오별: 추리 **-0.7(짐)**, 호러 +0.3, 로맨스 -0.3 → **전체 무승부~약간 열위.**
- **결론(정직):** 1차의 +0.6은 **100% 맥락 핸디캡 거품**이었다. 공정하게 재면 **단발 장면 변환에서 RAG 기여는 사실상 0** — 3턴짜리는 검색할 과거가 없기 때문(전부 프롬프트 안에 있음).
- **단발 변환 품질로 우리는 GPT/Gemini를 못 이긴다. 두 번 엄밀히 측정, 확정.**

### G-3. 그래서 이 비교(단발 변환)는 차별점 도구가 아니다

`evidence_report`(단발 3턴)는 **RAG가 작동하는 조건 자체가 아니다.** RAG의 무기는 "대화창 밖으로 밀려난 6턴 전 설정"을 끌어오는 것인데, 3턴 시나리오엔 밀려난 게 없다. 남은 결함:

- **단발 3턴** — RAG의 진짜 무기(장기기억)를 안 건드림. → 6턴+ 시나리오 필요(G-5).
- **n=3** — ±0.3은 노이즈 범위. "우위/열위" 단정 불가.
- **완성도 -0.3** — 우리 변환이 더 절제돼 "덜 완성된" 인상을 줄 때가 있는 실제 약점.

### G-4. 그래서 올바른 방향

- **공정한 ablation**: 베이스라인에도 **세계관+페르소나를 똑같이 주고**, **RAG 검색(장기기억)만** 제거 → 차이 = 순수 RAG. *(현재 미구현 — `evidence_report`의 `BASELINE_SYSTEM`에 world/persona 주입 필요.)*
- **단발 변환 품질로는 GPT/Gemini를 못 이긴다**(정직). 차별점 메인은 변환 점수가 아니라:
  - **`rag_demo`** — 6턴 전 설정 회상(맨손 실패 / 우리 성공) ⭐ **차별점 1순위**
  - **`consistency_demo`** — 설정 모순 탐지 ⭐ **차별점 2순위**
- 발표 킬러 = "문체가 좋다"(❌) → **"길이에서 기억·검수가 무너지지 않는다 — ChatGPT가 실제로 못 하는 것"**(✅, 라이브 시연으로 증명).

### G-6. 기억 RAG 정량 — `rag_recall_eval.py` (우리 진짜 차별점)

> evidence_report(단발)는 기억 RAG를 못 건드린다(generate_novel은 검색을 안 하고 전체 대화를 프롬프트에 통째로 넣음). 기억 RAG는 채팅 `/stream`에만 있으므로 **전용 스크립트로 분리해 측정**했다.

**방법(엄밀판):** 시나리오 4종 각각 — ①target 비밀 + **의미적으로 비슷한 방해 비밀 3개**(다른 인물의 '숨겨진 정체')를 함께 심고 ②잡담 11턴으로 target을 최근창(`PROMPT_HISTORY_LIMIT=10`) 밖으로 묻은 뒤 ③target을 물어 OFF/ON 각 3회(=12 trial). **심기는 POST만(생성 X)→스트리밍 안 해 rolling summary 미생성→OFF 깨끗.** 검색은 키워드, 응답은 독립 심판(Groq/Llama). `python -m scripts.rag_recall_eval`

> 이전(구버전)은 방해 문장이 의미적으로 멀어(커피·비) '심은 걸 그대로 꺼냄'(동어반복)이었다. 엄밀판은 **경쟁하는 방해 비밀** 속에서 옳은 것을 고르는지를 본다.

| 지표 | 결과 | 읽는 법 |
|------|:---:|------|
| 검색 recall@3 | 12/12 (100%) | 방해 속에서도 top-3에 target |
| **검색 top-1 정밀도** | **12/12 (100%)** ⭐ | **1순위가 항상 target** — 방해와 경쟁해 이김(동어반복 아님) |
| 방해 혼입(top-3) | 12/12 | top-3에 방해도 섞임(비밀 4개뿐이라 구조적) |
| 응답 일치 ON | 5/12 (42%) | 검색된 사실을 답에 반영(독립 심판) |
| 응답 일치 OFF | 3/12 (25%) | 깨끗한 OFF(요약 누수 제거) |
| **응답 차별점(ON−OFF)** | **+17%p** | 구버전 +33%p보다 낮고 정직 |

**정직한 해석:**
- **검색 자체는 진짜 강점.** 의미적으로 비슷한 방해 비밀 3개와 경쟁시켜도 **target이 항상 1순위(top-1 100%)**. 동어반복이 아닌 실제 retrieval 성능.
- **그러나 "검색 성공 ≠ 응답 반영".** 잠입형사는 **top-1 3/3로 찾았는데 응답 0/3**; 이중생활은 ON=OFF(이득 0). 모델이 검색된 기억을 **답에 항상 쓰지는 않는다.**
- **응답 차별점 +17%p** — 깨끗한 OFF + 방해 혼입(다른 비밀이 함께 주입돼 산만)으로 구버전(+33%p)보다 낮음. 이게 더 정직한 값.
- **한계:** n=12 데모 규모. 응답 단계 약함.
- **발표 포지셔닝:** 헤드라인은 "회상 100%"(과장)가 아니라 **"방해 속 검색 정밀도 top-1 100% — 단, 응답 반영은 +17%p로 약함"**. 라이브 `rag_demo`로 검색이 되는 걸 보여주되, 응답 반영 약점은 숨기지 않는다.

### G-7. 설정 모순 탐지 정량 — `consistency_eval.py` (출제 편향 제거판)

> **이전 결함:** 케이스를 내가 출제하고 내가 라벨링 → 선택·확증 편향(전부 100% 나옴).
> **개선:** **독립 모델(Groq/Llama)이 같은 케이스를 따로 분류** → (저자 vs 독립) 합의를 ground-truth로 삼고, 둘이 갈리는 항목(=내 편향/애매)을 드러낸다.

**방법:** 12세트·24항목(명백/미묘/애매) × 검수기 각 2회 + 독립 라벨 1회. `python -m scripts.consistency_eval`

| 항목 | 결과 | 읽는 법 |
|------|:---:|------|
| 라벨 합의(나↔독립) | 22/24 (92%) | 낮으면 내 라벨이 애매/편향 |
| 검수기 정확도 vs 내 라벨 | 21/24 (88%) | 내 라벨만 기준(편향 포함) |
| 검수기 정확도 vs 독립 라벨 | 23/24 (96%) | |
| **▶ 검수기 정확도 vs 합의셋** | **21/22 (95%)** ⭐ | 둘 다 동의한 것만 = 신뢰 |
| └ 합의셋 모순탐지(recall) | **12/12 (100%)** | 놓침 0 |
| └ 합의셋 정상통과(specificity) | **9/10 (90%)** | 오탐 1 |

**정직한 해석 — 편향이 실제로 잡혔다:**
- **내 출제 편향이 드러남.** 라벨 분쟁 2건이 **정확히 내가 '애매'로 넣은 케이스**(지아 회식 젓가락, 세라 발표). 거기서 **나=정상 / 독립=모순** — 내 라벨이 소수의견(내 '정상' 라벨이 항상 옳진 않았다).
- **그래서 합의셋 기준으로 본다 → 검수기 정확도 95%**(내 라벨만 보면 88%로 더 낮게도 나옴). 자기 유리한 기준을 안 쓴다.
- **합의셋 recall 100% / specificity 90%** — 모순은 안 놓치되 **정상 1건 오탐**(수아/김부장, 나·독립 둘 다 정상인데 검수기가 모순). **recall 편향**(놓치느니 잡는다) 재확인 — 창작 검수엔 옳은 방향이나 헛경고가 천장.
- **한계:** n=24(합의셋 22). 데모 규모. 독립 라벨러도 Llama(완벽한 정답 아님).
- **헤드라인:** "100% 만점"(거짓) → **"독립 교차검증 정확도 95%, 모순 recall 100%·정상 오탐 10%; 애매 케이스에선 내 라벨조차 독립과 갈렸다."**

### G-8. 개인화 RAG 인과 e2e — `personalize_e2e.py` (취향저격이 진짜 개인화되나)

> 저장 문장(`SavedSentence`)을 의미검색해 취향저격 추천의 근거로 주입하는 개인화 RAG(신규).
> **단순 "추천이 나온다"가 아니라, 저장 톤이 추천을 실제로 바꾸는지** 통제 실험으로 측정.

**방법:** **동일** 세계관·장면·작가(kimdohyeon), **저장 문장만 다른** 3명 — DARK(어둡고 단절적)/WARM(따뜻·서정)/NONE(저장 없음). 각자 `/author/taste-recommend` 3회 호출 → 추천을 **독립 심판(Groq/Llama)**이 톤 0~10(0=어두움, 10=따뜻)으로 블라인드 채점. `python -m scripts.personalize_e2e`

| 유저 | 저장 톤 | 추천 평균 톤 |
|------|------|:---:|
| **DARK** | 어둡고 단절적 | **4.0** |
| NONE | 없음(베이스라인) | 5.9 |
| **WARM** | 따뜻·서정적 | **6.9** |

- **개인화 효과(WARM−DARK) = +2.9점** · **DARK < NONE < WARM 완벽 단조** ✅ (교과서적 인과 패턴, NONE이 정확히 중간)

**정직한 해석:**
- **인과적으로 작동한다.** 같은 세계관·장면·작가인데 **저장 문장만 바꾸니** 추천 톤이 양방향 ±1.5점씩 갈리고 NONE이 중앙 → "저장 톤 → 추천 톤" 인과가 깨끗.
- **여기선 되고 스토리 생성(G-6 +17%p)에선 약한 이유:** 추천은 톤을 자유롭게 채택할 여지가 크고, 생성은 플롯·최근맥락에 묶임. → **"RAG는 생성보다 추천 층에 넣어라"는 판단이 데이터로 확인됨.**
- **베끼기 없음:** 추천은 저장 문장의 복붙이 아니라 톤만 흡수한 새 문장.
- **한계:** n 작음(유저당 8~9 추천), 심판 1명·1회, 효과 크기 ±1.5점(전면 override 아님 — 작가·장면이 중앙으로 당김).
